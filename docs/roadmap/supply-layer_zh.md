# 方向 7：供应层 — 把运维工具供应给外部服务器

## 状态：❌ 未开始

[English](./supply-layer.md)

## 目标

把 MiBeeHive 从"下载并存储"工具升级为**面向外部服务器的运维工具供应平台**：自动采集并持续更新运维工具，并按**已有的标准协议**对外暴露给外部服务器。指导原则：MiBeeHive 是供应链（采集→存储→供应）；它实现已有协议，让现成的工具能从它取料，而无需知道 MiBeeHive 的存在。

> **边界：** 这**不是**应用商店 / 建站（那是一般本机运维面板的领域）。本方向是**把运维工具供应给外部服务器集群**，不是在盒子上跑消费级应用。

## 两个子问题

本方向由两个独立、可组合的半边组成：

1. **爬取层（采集/更新）**——让新增数据源的采集变得廉价、可扩展。
2. **供应端点（对外服务）**——把采集到的制品按标准协议对外暴露给外部服务器。

## 爬取层：双轨制架构

并非所有源都一样。把一种机制硬套到所有源上，正是"难扩展"的根因。计划采用**双轨制**设计：

| 轨道 | 覆盖范围 | 扩展方式 |
|------|----------|----------|
| **规则指纹引擎** | 单页源：GitHub Releases（JSON）、结构化 JSON API（Crates.io、NPM）、HTML 列表页、静态目录列表 | 加源 = 加一份 YAML 指纹（数据驱动），类似 nmap 加探针。目标：**内置指纹库 + 用户运行时扩展**。 |
| **协议适配器** | 带有状态端点的真协议源：Go module proxy、PyPI、APT/YUM、OCI registry | 加源 = 写一个 Go 包实现适配器接口（代码驱动）。 |

现有 `Crawler` 接口（`FetchReleases(ctx, owner, repo)`）以 GitHub 为中心，正是摩擦点。双轨制设计**保留**现有 `CrawlManager`/`Scheduler` 编排层（它是健全的），只替换"源如何被描述和加载"这一层。

> **先验证再决定：** 一份 YAML 指纹能否覆盖足够多的源——尤其是多步源（例如 HashiCorp 的"版本目录→文件目录"两级结构）——是最大的悬而未决问题。必须先针对真实源做原型验证，再谈任何重写。见 Issue #1。

## 供应端点：协议优先级

采集到的制品应按标准协议对外供应，优先级如下（按 杠杆 ÷ 工作量）：

| 批次 | 协议 | 杠杆 | 工作量 | 备注 |
|------|------|------|--------|------|
| **1** | 软件工具仓库 + ISO 仓库 + Helm 仓库（`index.yaml`） | 极高 | **极低** | 现有采蜜的自然延伸（文件已存储；只需新增索引/协议布局）。优先交付。 |
| **2** | Go module proxy（`/goproxy/`） | 中高 | 中 | `GOPROXY` 协议清晰；已采集 `golang`。 |
| **2** | PyPI `/simple` / NPM registry | 中 | 中 | SOHO IT 常见；二选一先做。 |
| **3** | APT / YUM 仓库布局 | 高 | 中高 | 需生成 `Packages.gz`/`repomd.xml` 元数据；装机场景刚需但更重。 |
| **4** | OCI 镜像仓库 | 极高 | **极重** | OCI distribution spec（blob/manifest/内容寻址）复杂。评估转发到现成 registry vs 自建。 |

> `/metrics` 作为供应协议**不在范围内**——它仅保留用于 MiBeeHive 自身健康。MiBeeHive 把 `node_exporter`/`prometheus` **供应给**外部服务器；它不变成 TSDB。

## 运维模型

- **现在（轨道 A — 供应优先）：** MiBeeHive 是仓库 + 协议端点。外部服务器被动地从它取料。风险低、杠杆高。
- **以后（轨道 B — 主动运维）：** MiBeeHive 通过 SSH/agent 主动控制外部服务器（部署/更新/巡检）。叠加在稳定的供应层之上。复杂度更高；暂缓。

## 推进顺序（先验证）

1. **原型验证**规则指纹引擎，针对 4 个差异最大的真实源，端到端打通到通用文件仓库供应端点。产出诚实的报告。*(Issue #1)*
2. 基于报告**决定**：爬取层渐进重构 vs 重写 vs 放弃规则引擎。*(Issue #2)*
3. **第一批供应端点**（软件仓库 + ISO 仓库 + Helm）。*(Issue #3)*
4. 后续协议批次。

## 验收标准

- [ ] 规则引擎原型能用指纹成功覆盖单页源（JSON + HTML）；对多步源有明确结论。
- [ ] 指纹采集的制品能不经改动地流经现有下载/存储管线。
- [ ] 至少一个公开供应端点能按标准协议把采集制品供应给外部客户端。
- [ ] 记录决策：渐进重构 vs 重写，并附证据。

## 不在范围内

- 验证前修改主线 `Crawler` 接口 / DB schema / 前端。
- 真协议（Go proxy / PyPI / APT / OCI）——验证阶段只做通用仓库索引。
- 指纹的 Web UI / 热加载 UI（验证通过 fixture + 命令行进行）。
- 对外部服务器的主动远程控制（轨道 B，暂缓）。
